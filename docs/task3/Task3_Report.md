# Reversi Strategies Command History and Persistence

## Strategy pattern

The framework separates the rules for making a move from the rules for deciding who wins. All three Reversi variants use the same `ReversiGame`, opening position, eight-direction flanking algorithm and undoable placement command. Their factories inject different implementations of `IWinStrategy`. This avoids duplicating the game loop when only the objective changes.

`StandardReversiFactory` creates `MajorityWin`. This strategy returns `InProgress` while moves remain available and, at termination, compares the disk counts of the two players. `AntiReversiFactory` creates `MisereWin`, which uses the same counts but selects the player with fewer disks. Both strategies return a draw for equal counts. `CornerReversiFactory` creates `CornerDominanceWin`. It first checks whether either player owns at least three corners, even when the game is not terminal. Only when no player has corner dominance does a terminal game fall back to majority evaluation. `Game.AfterStateChange` evaluates the injected strategy after every move, so capturing the third corner finishes the match immediately.

Termination and victory are separate concerns. The inherited `Game.IsTerminal` determines whether both players have no legal placement. This also detects a full board and positions that cannot continue despite having empty cells. A player with no placement must pass while the other player can still move. `ReversiGame.Validate` accepts `PASS` only when the active player has no legal placement; the shared loop builds `PassCommand`. Computer players pass automatically without calling their strategy with an empty list.

Computer behaviour is a second use of Strategy. `IComputerStrategy.Choose` receives the authoritative `GameState`, the computer player and the already computed legal placements. `SmarterReversiStrategy` is configured with a `ReversiObjective`. The majority objective maximises the number of flipped disks. The misere objective penalises corner capture and otherwise minimises flips. The corner objective gives the highest score to an immediate third-corner victory, then avoids moves that allow the opponent to capture a third corner on their next move. It subsequently prioritises corner capture, reduces the opponent's available corner moves and maximises flips. This is a tactical one-ply heuristic; it does not claim exhaustive search or optimal play.

`SmarterGomokuStrategy` implements the same interface. It first searches the supplied legal ordinary and heavy placements for an immediate five-in-a-row win in the four alignment directions. If no winning move exists, it counts empty cells at which the opponent could complete five and evaluates legal responses by the number of threats remaining. This detects both contiguous fours and internal gaps. A legal Eraser move can remove a stone from an open four and neutralise threats at both ends; legality and inventory availability remain the responsibility of the Gomoku game. If there is no urgent win or block, the strategy extends its own longest alignment and prefers positions near the centre. Stable tie-breaking prefers ordinary stones to preserve special inventory. Consistent with the team contract, Fog AI reads the true board.

AI evaluation never changes the live board, history or inventories. Gomoku uses an overlay when considering a placement or removal. Corner Reversi uses a separate copied board to calculate opponent replies. The returned input is always an item in the supplied legal list.

The concrete game depends on `IWinStrategy` and the computer player depends on `IComputerStrategy`, which demonstrates dependency inversion. The strategies each have a single responsibility. A new Reversi victory objective can be added by implementing `IWinStrategy` and registering a factory without changing `Game.Play`, demonstrating the open/closed principle. All strategies satisfy the common contract, including a win or draw when a game is terminal, supporting substitutability.

## Command pattern

`IMoveCommand` defines the common `Execute`, `Undo` and `ToRecord` operations. `Game` creates a command for a validated input, and `CommandHistory` invokes it. `ReversiPlaceCommand` is the concrete command for placing and flipping disks; `GameState` and its `Board` are the receivers. `PassCommand`, supplied by Core, participates in the same history while leaving the board unchanged.

On its first execution, a `ReversiPlaceCommand` asks `ReversiRules.GetFlips` for all flanked positions. It stores a `CellChange` for the new disk and one for every captured disk. Each change contains its position, immutable `Before` piece and immutable `After` piece. A flip replaces a piece rather than mutating its owner. All changes are sent to `Board.Apply` together. The board validates every expected prior value before applying the batch and raises one `BoardChanged` event for the entire move. The command does not maintain a second disk counter; counts are derived from the current board and therefore automatically follow undo and redo.

`Undo` applies the inverse of every stored change: the newly placed disk disappears and all captured disks recover their original colours. `Execute` reuses the retained changes on redo. Consequently, undo and redo use the same recorded before/after values rather than recalculating the original capture against a different board. The eight-direction command test executes, undoes and re-executes a placement that captures eight disks and checks both state restoration and event batching.

The shared `CommandHistory` retains applied commands in `_undo` and undone commands in `_redo`. A full-turn undo removes two commands in reverse order. Redo applies those commands in chronological order. Since `GameState.Current` is derived from `MoveCount % 2`, undoing a pair returns control to the requesting player in both HvH and HvC. A `PASS` counts as one command in the pair. Fewer than two available commands cannot be undone as a full turn. Any new command clears redo history. These policies are supplied by Task 1; Task 3 integrates them rather than introducing a competing history mechanism.

`MoveRecord` is the command's persistent representation: actor index, move code and coordinates, with null coordinates for a pass. `JsonGameRepository` implements `IGameRepository` in a separate project depending only on Core. Saving calls `Game.ToSaveData`, which captures family, variant, mode, AI level, board snapshot, inventories and the applied move records. Active player and turn number are derivable from the number of records. The repository writes a temporary file in the destination directory before replacing an existing save.

Loading validates the JSON schema, enum values, save version and move records, then resolves the factory through `GameCatalog`. The factory constructs a fresh game with its normal board, players, rules and view. `Game.Replay` validates and executes each record through the regular command path, rebuilding the actual undoable commands. The repository rejects a move recorded after a terminal result. It suppresses automatic drawing during replay, restores the view's drawing setting afterwards, and verifies the reconstructed board and inventories against the saved values before returning the new game. An invalid save never replaces the currently running game because `MainMenu` switches games only after `Load` succeeds. If the loaded result is already complete, the menu displays the board and winner or draw without requesting another move.

This implementation preserves the applied command history and provides immediate full-turn undo after loading. Redo history is deliberately omitted according to the team contract. The repository requires neither a reference to Reversi nor a special branch for GomokuPlus. Special inventories are reconstructed by the registered game's commands and checked generically. Fog's perspective is reconstructed by its attached view as history is replayed; final integration with Task 2's actual view and Eraser command remains necessary.

## Verification evidence

At this Task 3 checkpoint, `dotnet build BoardGames.slnx -warnaserror` and `dotnet test BoardGames.slnx --no-build` pass. The suite contains 193 passing cases, comprising the 50 existing cases and 143 added Task 3 cases. Coverage includes all eight capture directions, unbounded and interrupted lines, rejection without mutation, disk restoration, full-turn undo and redo, history branching, forced passes, majority and misere results, draws, third-corner victory, tactical AI choices, complete matches and persistence validation.

Twenty-four complete seeded HvH matches compare every legal move list against an independently written endpoint-based oracle. Nine complete HvC matches exercise the Smarter strategy through the actual shared loop. Repository round trips cover all six currently registered variants, both modes and both AI levels. Reversi tests use the implemented rules; the Gomoku round trips currently exercise Task 1's placeholder rules. Additional tests load a real forced-pass history, restore undo after restart, reject inconsistent saves and preserve the current game after a failed in-game load.

The three assignment Reversi CLI examples execute successfully. The standard and anti examples finish with X=5, O=4, P2 active. The corner example finishes with X=5, O=5, P1 active. These examples remain in-progress matches; they do not demonstrate complete victory conditions. The dedicated full-match and corner-dominance tests provide that evidence.
